# Contributing Guidelines

This document describes how to propose, format, and submit changes to **homebrew-openframe**, the Homebrew tap that distributes the OpenFrame CLI and client as Homebrew formulae/casks. It covers code style, branch naming, the pull request process, commit message format, and the checklist a reviewer applies before merging.

> This repository is a Homebrew tap. Most of its content is plain-text Ruby formula/cask definitions, repository metadata (`.github/CODEOWNERS`), and the generated automation workflows under `.github/workflows/`. Keep changes small and reviewable: a tap lives or dies on reviewers being able to trust every diff at a glance.

## Where this fits

According to the organization's repository graph, this repository currently publishes no artifact that another repository pins, and no repository is recorded as a consumer of it. Coverage of that graph is **partial** — two related repositories (OpenFrame CLI, OpenFrame OSS Tenant) and one repository not visible from here are not indexed, so an empty consumer list does not prove nothing depends on this tap. ## Code owners

All paths in this repository are currently owned by `@flamingo-stack/devops-engineers`, as declared in `.github/CODEOWNERS`:

```text
*                          @flamingo-stack/devops-engineers
```

`.github/CODEOWNERS` uses last-match-wins semantics: broader patterns must stay above more specific ones. If you add a narrower ownership rule for a subdirectory (for example a future `Formula/` or `Casks/` owner), add it **below** the existing `*` line, not above it, or it will never take effect.

## Code style and conventions

### General principles

- **Keep formula/cask diffs minimal and mechanical.** A tap's trust model depends on every version bump being a small, obviously-correct diff (URL, checksum, version string). Do not bundle unrelated refactors into a version-bump PR.
- **Never hand-edit a generated workflow file.** `.github/workflows/code-documentation.yml` and `.github/workflows/flamingo-code-review.yml` are generated and installed by the Flamingo hub's "Setup Workflow", and are explicitly marked as such:
  - `code-documentation.yml` documents itself as "Installed into a target repository by the multi-platform hub (Setup Workflow). The hub dispatches it to generate this repository's documentation and open a pull request with the result."
  - `flamingo-code-review.yml` opens with "Generated by the Flamingo hub — do not edit by hand. Per-repo settings live in the hub admin (/admin/code-review); this file is byte-identical across every reviewed repository AND every deployment, which is what makes drift detectable by comparison."

  If a change to either file seems necessary, it belongs in the hub's templates, not as a direct edit here — a direct edit breaks the byte-identical drift check the review workflow relies on.
- **Never pin a script hash inside workflow YAML.** Scripts the workflows fetch from the hub (`/api/ci/scripts` or the deprecated `/api/doc-orchestrator/scripts` alias) must be verified through the shared `download_and_verify` function against the hub's `manifest.json` digest — never against a SHA pinned in the workflow file itself (the `HASH_*` env var mechanism is retired). Do not reintroduce `curl | bash`, do not execute or source a fetched script before verification, and do not hand-roll a variant of `download_and_verify`.
- **Respect fork-sentinel conventions where they apply.** Some of the surrounding OpenFrame ecosystem enforces `// >>> OPENFRAME(<slug>): <why>` / `// <<< OPENFRAME(<slug>)` sentinel comments around edits to files that originate upstream. If you are editing a file in this tap that mirrors or vendors content from an upstream project, preserve that convention rather than silently diverging.
- **One source of truth for every fact.** Do not duplicate a constant, label, version string, or URL in two places when one already owns it (for example, a version number that appears in both a formula and a changelog entry should be updated in lockstep, and ideally derived rather than retyped). If you find the same value hardcoded in two files, prefer fixing the duplication over adding a third copy.

### Ruby (formula/cask) conventions

Where this tap defines Homebrew formulae or casks, keep to idiomatic Homebrew style:

- Match the formatting Homebrew itself expects (two-space indentation, double-quoted strings for interpolation, single-quoted otherwise) so that `brew audit` and `brew style` pass cleanly.
- Keep `url`, `sha256`, and `version` fields together and update them as a single atomic change — never land a URL bump without its matching checksum.
- Avoid inline comments that merely restate the field name; comment only non-obvious choices (e.g., why a particular release channel or mirror is used).

### YAML / workflow conventions

- Keep generated workflow files untouched except through the hub's setup/update flow described above.
- In any YAML you do author directly (e.g., repository metadata), keep keys and values quoted consistently and avoid introducing unquoted values that could be misread as other types.

## Branch naming and PR process

### Branch naming

Use short, descriptive branch names that signal intent at a glance. Follow the conventions already visible in this repository's own automation, which reserves certain prefixes for specific automated purposes — avoid colliding with them:

| Prefix | Reserved for | Notes |
|---|---|---|
| `setup/` | The hub's own setup PRs (workflow installation) | Do not use for manual branches; the review workflow explicitly excludes branches with this prefix from its code-graph triggers. |
| `code-documentation/` | Automated documentation pipeline PRs (`DOCS_BRANCH_PREFIX`) | Reserved for the documentation pipeline's own branches. |
| `ai-fix/` | Automated fix branches | Explicitly excluded from the code-graph trigger condition. |

For your own contributions, prefer a pattern such as:

- `fix/<short-description>` — bug fixes (e.g., a broken checksum, a stale download URL)
- `feat/<short-description>` — new formula/cask additions or new automation
- `chore/<short-description>` — maintenance that is neither a fix nor a feature (dependency bumps, CODEOWNERS changes)
- `docs/<short-description>` — documentation-only changes

Keep the slug short, lowercase, and hyphenated.

### PR process

1. **Open the PR against the default branch.** The default branch is what the code-graph job re-indexes on every push (see `.github/workflows/code-documentation.yml`'s `push` trigger, which ignores `docs/**` and `**.md` changes so that a documentation merge never triggers a rebuild of the graph).
2. **Keep the diff scoped.** A formula/cask bump, a CODEOWNERS change, and a workflow update are three different PRs unless they are causally linked.
3. **Let automated review run.** This repository has the Flamingo Code Review workflow installed (`.github/workflows/flamingo-code-review.yml`). Depending on how the PR is opened, review either runs automatically or must be requested:
   - Opening, reopening, or marking a PR ready for review posts an **invitation** comment rather than running a review immediately — review starts only when you act on it (checking its box, commenting, or applying a label).
   - To request a review explicitly, comment `@flamingo-review` on the PR (use `@flamingo-review full` to force a full re-read of the cumulative diff rather than only the incremental delta since the last review).
   - Alternatively, apply the `flamingo-review` label from the sidebar; it is a one-shot request and is automatically consumed (removed) once processed. The `flamingo-review-always` label is different: it is durable and subscribes the PR to review on every subsequent push.
   - None of this works from a fork with write-restricted tokens in the same way — review logic explicitly checks `head.repo.full_name == github.repository` before proceeding, and a comment-triggered review additionally requires the commenter to have `OWNER`, `MEMBER`, or `COLLABORATOR` association.
4. **Address findings.** Respond to review comments in the PR thread; push follow-up commits to the same branch.
5. **Merge once checks are green and review is satisfied.** Do not force-push over a review that is in progress unless you intend to ask for a fresh pass (a full re-review can be requested with `@flamingo-review full`).

> Because downstream consumption of this tap by other repositories is only partially indexed (OpenFrame CLI and OpenFrame OSS Tenant are not currently indexed from here), do not assume a formula/cask change is "internal only." Treat version and URL changes as externally visible — they are what end users' `brew install` commands resolve.

## Commit message format

Write commit messages that explain **why**, not just what changed — the diff already shows what changed. Follow these conventions:

- **Subject line**: imperative mood, no trailing period, ideally under ~72 characters. Example: `Bump openframe-cli cask to v1.4.2`.
- **Reference the affected formula/cask by name** in the subject when the change is version-scoped, so the history is scannable: `Fix sha256 for openframe stage channel cask`.
- **Body** (when the change is non-trivial): explain the reason for the change — a new upstream release, a broken download URL, a checksum mismatch, an added release channel — and link the relevant upstream release or issue if one exists.
- **Keep automation-authored commits distinguishable.** Commits produced by the documentation pipeline or the code-review bot are not something you should imitate by hand; if you are writing a commit yourself, make it clearly human-authored and specific to the change.
- **Squash fixup commits before merge** where the PR history is just "wip" / "fix typo" cycles, so the merged history reads as one coherent change per logical unit of work.

Example of a good commit message:

```text
Add dev channel cask for openframe-client

Upstream now ships a `dev` release channel alongside `stage` and
stable. This adds the corresponding cask so `brew install --cask
openframe-client-dev` resolves to it, matching the pattern already
used for the stage channel.
```

## Review checklist

Before requesting review (or before approving one), confirm:

- [ ] **Scope.** The PR does exactly one logical thing — a version bump, a new formula/cask, a metadata change, or a docs change — not a mix.
- [ ] **Formula/cask correctness.** Any `url`, `sha256`, and `version` fields that were touched were touched together and are internally consistent (the checksum matches the file at that URL).
- [ ] **No hand-edited generated files.** Neither `.github/workflows/code-documentation.yml` nor `.github/workflows/flamingo-code-review.yml` was edited directly outside of the hub's setup/update flow. If a workflow file appears in the diff, confirm it came from a hub-dispatched setup PR, not a manual edit.
- [ ] **No pinned script hashes reintroduced.** Any workflow change does not add a `HASH_*` env var or otherwise bypass `download_and_verify` / `load_script_manifest` for a hub-served script.
- [ ] **CODEOWNERS integrity.** If `.github/CODEOWNERS` was touched, broader patterns remain above narrower ones (last-match-wins), and the change does not accidentally remove `@flamingo-stack/devops-engineers` coverage from a path that needs it.
- [ ] **Branch name does not collide with reserved prefixes.** The branch is not accidentally using `setup/`, `code-documentation/`, or `ai-fix/`, which are reserved for automation.
- [ ] **Commit messages are meaningful.** The subject is imperative and specific; fixup/wip commits are squashed.
- [ ] **No duplicated source of truth.** A version string, URL, or constant was not retyped in a second place when an existing field already owns it.
- [ ] **User-facing impact considered.** If this change affects what `brew install`/`brew install --cask` resolves to, the corresponding install/upgrade/uninstall documentation still describes the correct behavior (see the linked how-to guides above).
